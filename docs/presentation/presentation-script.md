## 1 · 표지 (0:17)

안녕하세요. Bean 팀 고광근입니다.
저희가 4주 동안 만든 건 온프레미스와 AWS를 하나로 묶은 하이브리드 보안 플랫폼입니다.
무엇을 어디까지 실제로 돌려봤는지 말씀드리겠습니다.

## 2 · 목차 (0:20)

오늘 순서는 다섯 개입니다.
주제를 고른 이유와 팀 구성은 짧게 짚고, 네 번째 수행 결과에 시간을 가장 많이 쓰겠습니다.
구조를 먼저 보여드리고 그 위에 접근 통제와 공급망, 모니터링을 얹는 순서로 가겠습니다.

## 3 · 침해 사례 (0:40)

계기는 실제 사고들입니다.
쿠팡은 전직 내부 직원 한 명이 회원 3,370만 건을 빼냈습니다. 외부 침입이 아니라 권한을 이미 가진 사람이었고요.
패스트캠퍼스는 GitHub 마스터 계정 키값 하나가 탈취되면서 뚫렸습니다.
KT는 불법 초소형 기지국으로 가입자 식별번호가 샜고,
YES24는 랜섬웨어로 멈춘 뒤 두 달 만에 또 맞았습니다.
원인은 다 다른데, 결과를 가른 건 권한과 비밀 정보, 복구 준비였습니다.

## 4 · 문제 정의 (0:27)

그래서 세 가지를 기준으로 잡았습니다.
접근 권한을 한 곳에서 관리할 수 있는지, 비밀 정보가 코드에 남지 않는지,
장애가 났을 때 되짚을 기록이 남는지입니다.
이걸 온프레미스에서만 풀면 반쪽이라고 봤습니다.
실제 환경이 하이브리드니까 저희도 양쪽을 같은 규칙으로 묶기로 했습니다.

## 5 · 팀 구성 (0:35)

팀은 다섯 명입니다.
저는 OPNsense와 Proxmox, k3s 기반과 공급망, 통합 인증을 맡았습니다.
이진희 님이 Prometheus와 Grafana로 관측과 알림을, 박재윤 님이 AWS VPC와 CIEM, CSPM 거버넌스를,
박수근 님이 OpenTofu로 EKS 인프라와 테스트 코드를,
정주헌 님이 웹서비스 설계와 접근 시나리오 검증을 맡았습니다.

## 6 · 4주 일정 (0:24)

기간은 4주였습니다.
첫 주는 아키텍처 설계와 역할 배분, 2주차에 인프라를 올리면서 보안 단계를 잡았습니다.
3주차에 각자 만든 걸 붙였는데 사실 이때 오류가 제일 많이 나왔습니다.
마지막 주에 통합 테스트와 데모 영상, 발표 자료를 정리했습니다.

## 7 · 물리 경계 (0:46)

이 그림 한 장이 저희 플랫폼 전부입니다. 앞으로 네 장은 같은 그림에서 보실 곳만 바뀝니다.
먼저 들어오는 길인데요, 공개된 진입점은 NetBird 컨트롤 릴레이와 Cloudflare 뒤 SSO 프런트엔드 둘뿐입니다.
나머지는 내부 DNS에서만 보이고, 그 앞은 OPNsense가 막습니다.
안쪽은 전부 Proxmox 한 대 위에 있습니다. 이게 죽으면 다 죽습니다.
그래서 그림에도 허용한 SPOF라고 적었는데, HA를 포기한 대신 다시 세우는 쪽에 시간을 썼습니다.

## 8 · 온프레미스 플랫폼 (0:36)

그 한 대 안에는 k3s 하나에 네 묶음이 올라가 있습니다.
접근·인증, 공급망·배포, 탐지·사람 승인, 보호·복구입니다.
아래 VM 네 개는 밖으로 뺐습니다.
Postgres와 SeaweedFS S3, Warpgate, NetBird인데 상태를 가졌거나 권한이 다릅니다.
장애 도메인을 나눈 건 아닙니다. 노드는 한 대니까요.
업데이트와 권한, 복구 단위를 나눈 겁니다.

## 9 · HR System 워크로드 (0:44)

오른쪽 AWS입니다. 대표 워크로드는 HR System 하나고요.
EKS는 private endpoint로 열었고, 안에 포털 화면인 frontend와
직원 API employee-service, 관리 API hr-service가 있습니다.
셋 다 internal ALB 뒤라 인터넷에서 직접 닿지 않고, 데이터는 private 서브넷 Aurora로 들어갑니다.
권한은 AWS 자원 쪽은 IRSA가, DB 접속 정보는 Secrets Manager가 맡습니다.

## 10 · EKS까지의 보안 흐름 (0:35)

사용자는 어떻게 여기까지 갈까요. 초록색 길이 그 경로입니다.
HR 포털을 열면 온프레미스의 Traefik과 Pomerium을 먼저 지나면서 Keycloak 신원을 확인받고,
그 다음 Site-to-Site VPN을 타고 AWS로 들어갑니다.
중요한 건 두 영역을 잇는 사설 경로가 이 VPN 하나뿐이라는 점입니다.
HR 서비스는 인터넷 쪽 입구가 없습니다.

## 11 · AWS 보안·관측 (0:28)

AWS 안쪽 보안과 관측은 이 아래 블록입니다.
GuardDuty가 위협을 잡고 Security Hub가 findings를 모읍니다.
Config와 Access Analyzer가 구성과 권한을 계속 훑고요.
로그는 CloudWatch와 Security Lake로 모여 Athena로 조회합니다.

## 12 · 온프레미스 보안 ① (0:41)

그 위에 올린 도구입니다. 먼저 접근 쪽인데요.
바깥 경계는 OPNsense가 1차로 막습니다.
방화벽과 NAT, VLAN 분리, 내부 DNS가 여기 있고 Suricata도 붙어 있습니다.
원격 접속은 NetBird로, 승인된 사용자와 기기만 암호화된 터널로 붙습니다.
인증은 SSO를 Keycloak이 맡고, Pomerium이 서비스 앞단에서 매번 권한을 다시 확인합니다.
한 번 로그인했다고 계속 통과시키지 않습니다.

## 13 · 온프레미스 보안 ② (0:41)

나머지 넷은 안쪽을 지킵니다.
CrowdSec은 웹 앞단에서 SQL 인젝션이나 XSS를 막습니다. OWASP 코어 룰셋을 붙였고요.
Warpgate는 특권 세션 게이트웨이입니다.
SSH나 DB에 직접 붙지 않고 전부 여기를 거치는데, MFA를 넘어야 세션이 열립니다.
Wazuh는 SIEM 겸 XDR을 맡고요.
Vault는 DB 비밀번호나 API 키를 코드에 남기지 않고 중앙에서 주입합니다.
아까 본 키값 탈취를 막는 자리입니다.

## 14 · 접근 통제 (0:47)

접근 통제는 셋으로 쪼갰습니다. 누가 들어오는지, 어디까지 가는지, 무엇을 만지는지입니다.
신원은 Keycloak 한 곳에서만 만듭니다. 일상 ID 다섯 개와 특권 ID 하나,
여섯 개 전부 MFA를 걸었고 서비스마다 로컬 계정을 따로 만들지 않습니다.
경로는 Pomerium입니다. Route마다 그룹을 다시 확인하고 Host와 Path 단위로 막습니다.
마지막이 중요한데, Pomerium을 통과했다고 관리자 권한이 생기지는 않습니다.
실제 권한은 애플리케이션이 다시 판단합니다.

## 15 · HR 품질·공급망 (0:58)

공급망이 가장 공을 들인 부분입니다. 코드가 뜨기까지 관문 여섯 개를 지납니다.
Jenkins에서 테스트와 커버리지를 돌리고 SonarQube 게이트를 넘습니다.
Trivy로 스캔해 SBOM을 뽑고 Cosign으로 서명합니다.
통과한 이미지만 Harbor에 올라가고, 올라간 digest만 ECR로 복제됩니다.
마지막에 EKS의 Kyverno가 서명을 다시 확인합니다.
왼쪽이 실제로 끊긴 빌드입니다. 42번이 test and coverage gates에서 멈췄는데,
뒤 단계가 그려지지도 않았습니다. 이미지 자체가 안 만들어진 겁니다.
Argo CD는 이 관문을 다 통과한 digest만 선언에 씁니다.

## 16 · AWS 보안 (0:34)

AWS는 세 축입니다.
네트워크는 인터넷과 맞닿는 자리에 ALB만 두고 NAT와 EKS 노드, RDS는 private 서브넷에 넣었습니다.
밖에서 직접 부를 수 있는 게 없습니다.
자격 증명은 영구 키를 만들지 않고, Keycloak OIDC를 연동해 STS 임시 토큰을 받아 씁니다.
이어서 IRSA, CIEM, CSPM 순서로 보여드리겠습니다.

## 17 · IRSA (0:43)

먼저 Pod 권한입니다. EKS에서 흔한 실수가 노드 전체에 권한을 몰아주는 건데요.
그러면 그 노드 Pod가 전부 같은 권한을 갖습니다.
저희는 IRSA로 서비스 어카운트를 IAM OIDC에 연결해 Pod 단위로 역할을 붙였습니다.
employee-service와 hr-service가 쓰는 권한이 다릅니다.
Aurora나 Secrets Manager를 부를 때는 STS가 짧게 사는 임시 토큰을 내줍니다.
이미지에 키를 넣을 일이 없습니다.

## 18 · CIEM (0:43)

다음은 권한 관리입니다. 권한은 처음에 잘 줘도 시간이 지나면 늘어납니다.
IAM Access Analyzer가 CloudTrail 로그를 분석해 일정 기간 안 쓴 권한을 찾아 지웁니다.
반대로 EventBridge가 로그를 실시간으로 보다가 핵심 권한을 건드리는 시도가 잡히면
Lambda가 바로 끊고 Slack으로 알립니다.
온프레미스 탐지는 사람 승인 앞에서 멈추는데, CIEM만 권한 변조라는 좁은 조건에서 자동으로 끊게 뒀습니다.

## 19 · CSPM (0:40)

세 번째는 상시 감사입니다. 콘솔을 매번 볼 수는 없으니까요.
Security Hub 보안 표준 점수를 지표로 잡고 계속 고쳐서 92%까지 올렸습니다.
Critical과 High는 남기지 않는 게 기준입니다.
EC2에 IMDSv2를 강제해 토큰 없이는 자격 증명을 못 꺼내게 했고, S3 버킷에는 MFA Delete를 켰습니다.
오른쪽이 실제 알림인데, 리소스 이름과 확인할 쿼리까지 붙어서 Slack으로 옵니다.

## 20 · 운영 모니터링 (0:39)

모니터링은 두 갈래입니다.
잘 돌고 있는지 보는 운영 쪽, 공격받고 있는지 보는 보안 쪽인데 먼저 운영입니다.
Grafana 대시보드 10종으로 자원 사용률과 Traefik 트래픽, 백업, Argo CD 동기화를 봅니다.
로그는 Loki로 모아 error와 warn만 걸러 보고요.
알림은 Prometheus 상시 경보 19개인데 이 중 9개가 백업입니다.
설정이 아니라 어젯밤에 실제로 돌았는지를 봅니다.

## 21 · 보안 모니터링 (0:53)

보안 쪽은 Wazuh로 호스트 7대의 파일 무결성과 rootcheck, 앱 로그 6종, NetBird 감사 이벤트를 모읍니다.
왼쪽이 최근 24시간인데 21만 8천 건입니다.
가운데가 잡힌 예인데, Proxmox 설정 디렉터리가 바뀌면 rule 550, level 7로 올라옵니다.
여기서부터는 저희 규칙인데, 등급이 경로를 정합니다.
level 7은 Shuffle이 정보를 붙여 사람 승인 앞에서 멈춥니다.
계속할지 멈출지는 오른쪽처럼 사람이 고르고, level 14 이상만 즉시 통지됩니다.
그래서 active_response는 0건입니다.

## 22 · SWOT (0:35)

자체 평가입니다.
강점은 다시 세우는 것과 서명을 확인하는 게 실제로 돈다는 점입니다.
구성이 전부 Git에 있어서 지금 뭐가 떠 있는지 코드로 확인됩니다.
약점은 물리 노드가 한 대라 HA가 없다는 거고, 실시간 대응도 부족해서 지금은 사람이 승인해야 움직입니다.
노드가 한 대만 더 생기면 장애 도메인을 진짜로 나눌 수 있고, 그때 손댈 건 IaC 코드뿐입니다.

## 23 · 마무리 (0:19)

정리하면 저희가 4주 동안 확인한 건 세 가지입니다.
접근은 한 곳에서 통제되고, 검증을 못 넘은 이미지는 배포되지 않고, 이상 징후는 사람 앞까지 옵니다.
발표 마치겠습니다. 감사합니다.

## 발표 중 주의

- **7~11장은 같은 그림이다.** 7장 첫 문장에서 이 사실을 먼저 말하지 않으면 청중이 매번 새 그림을 읽으려 한다.
  강조된 초록 테두리만 손으로 짚고 넘어간다.
- **11장과 18장은 자동 대응 범위가 다르다.** 11장 그림 안 문구는 조치를 사람이 승인한다고 말하고,
  18장은 Lambda가 자동으로 끊는다고 말한다. 18장 마지막 줄이 이 차이를 설명하는 자리이므로 빼고 읽지 않는다.
  질문이 들어오면 온프레미스 탐지는 사람 승인, AWS 권한 변조만 자동 차단이라고 답한다.
- **21장 rule 550은 Proxmox 설정 디렉터리 변경 감지다.** 경로를 그대로 읽지 말고 화면을 가리킨다.
