# ADR-0011: AWS 사설 연동을 policy-based Site-to-Site VPN으로 구현

- 상태: `Accepted`
- 날짜: 2026-07-31
- 관련 작업: `AWS-NET-01`, `BKP-04`, `NET-03`, `NET-04`, `KMS-01`

## 배경

[`architecture.md`](../architecture.md)는 OPNsense와 AWS VPC를 Site-to-Site VPN으로
잇는다고 이미 정했다. 남은 것은 구현 형태다. 토폴로지, 라우팅 방식, state 경계와
"이 연결이 상시 존재하는가"는 나중에 바꾸기 비싸고, 잘못 고르면 랩의 두 가지 성질을
동시에 해친다.

첫째는 비용이다. 이 랩의 AWS 사용량은 오프사이트 bucket 하나뿐이라 사실상 무료
구간에 있다. VPN Connection은 트래픽과 무관하게 존재하는 시간에 비례해 과금되므로,
연결 하나가 계정 전체 비용을 지배한다. 어떤 선택은 그 위에 attachment 요금을 더 얹는다.

둘째는 경로의 예측 가능성이다. `NET-03`이 만든 경계는 각 VLAN이 RFC1918 목적지를 먼저
차단하고 공개 Web만 내보내는 구조다. 여기에 동적 라우팅을 끌어들이면 학습한 경로가
기본 경로나 VLAN 간 경계를 바꿀 수 있고, 그 변화는 방화벽 규칙을 읽어서는 보이지 않는다.

## 결정

**VGW를 쓰고 Transit Gateway를 쓰지 않는다.** 연결할 VPC가 하나, 온프레미스 사이트가
하나다. TGW가 제공하는 다중 VPC 라우팅 허브는 이 구조에서 쓸 데가 없는 반면 attachment
시간당 요금과 데이터 처리 요금이 새로 붙는다.

**BGP를 쓰지 않고 static routing으로 고정한다.** 터널은 미리 적은 대역만 나른다.
동적 경로를 학습하지 않으므로 터널이 살아나거나 죽는 것이 온프레미스나 VPC의 기본
경로를 바꿀 수 없다. 이것이 "인터넷 기본 경로 불변"을 검증이 아니라 구성으로 보장하는
부분이다. 부수적으로 OPNsense에 라우팅 데몬을 설치하지 않아도 되어 복구 독립성을 지킨다.

**policy-based로 구성하고 traffic selector를 양쪽 대역으로 좁힌다.** 지정한 대역 밖의
트래픽은 IPsec SA 자체에 실리지 않는다. 대역 제한이 방화벽 규칙 하나에만 걸려 있지 않고
암호화 계층에서 먼저 강제된다. 온프레미스 쪽 selector는 랩 전체가 아니라 실제로 AWS와
통신할 VLAN 하나로 시작한다.

**AWS 쪽 VPC에 인터넷 gateway를 두지 않는다.** 이 VPC의 유일한 외부 경로가 VPN이라는
사실이 "대상 대역만 통신"을 구조로 만든다. 사설 착지점이 공개 진입면으로 자라지 않는다.

**오프사이트 백업 root와 state를 공유하지 않는다.** 두 계층은 수명주기가 다르다.
백업 bucket은 지워지면 안 되는 자산이라 `prevent_destroy`가 걸려 있고, VPN은 비용 때문에
언제든 내릴 수 있어야 하는 설비다. 한 state에 두면 그 두 요구가 서로를 막는다.

**연결 자체를 gate 변수로 둔다.** 닫으면 과금 자원이 0이 되고 VPC·서브넷·VGW만 남는다.
검증이 끝난 뒤 연결을 유지할지는 그때의 필요로 결정하며, 유지하지 않기로 해도 착지점
구조와 검증 절차는 그대로 남는다.

**기존 공인 AWS API 경로를 이 VPN으로 옮기지 않는다.** 오프사이트 백업은 계속 공인
endpoint로 나간다. 백업 경로가 VPN에 의존하면 터널 장애가 곧 백업 중단이 되고, 복구
수단이 복구 대상과 얽힌다.

## 검토한 대안

- **Transit Gateway:** 나중에 VPC가 늘어날 때 유리하지만 지금은 쓰지 않는 기능에
  attachment 요금을 상시 지불한다. VPC가 둘 이상 필요해지면 그때 다시 결정한다.
- **BGP 동적 라우팅:** 터널 장애 전환이 빠르고 대역 추가가 자동이다. 그러나 학습한
  경로가 기본 경로에 영향을 줄 수 있고, 그 위험을 막으려면 필터를 또 검증해야 한다.
  대역이 하나뿐인 구성에서 얻는 것보다 잃는 예측 가능성이 크다.
- **route-based(VTI) 터널:** 터널 두 개를 동시에 쓰기에 명확하고 대역 추가가 route
  변경으로 끝난다. 대신 OPNsense에 VTI 인터페이스와 route를 새로 만들어야 해서 라우팅
  변경면이 넓어진다. 터널 이중화가 실제로 필요해지면 이 방식으로 전환한다.
- **AWS 쪽 터널 두 개를 모두 온프레미스에 구성:** 추가 요금은 없지만 policy-based에서
  같은 selector로 두 SA를 유지하면 어느 쪽이 활성인지 불명확해진다. 단일 WAN 회선이라
  터널을 이중화해도 온프레미스 쪽 단일 장애점은 그대로 남는다.
- **default VPC 재사용:** 만들 자원이 줄지만 공개 서브넷과 인터넷 경로가 이미 붙어 있어
  "사설 경로만"이라는 판정을 흐린다.
- **연결을 만들지 않고 공인 endpoint만 사용:** 비용이 0이다. 그러나 사설 연동 경로를
  검증한 적 없는 상태가 유지되고, 실제로 필요해지는 시점에 처음 시도하게 된다.

## 결과

- 온프레미스 WAN이 ISP DHCP 임대 주소라 주소가 바뀌면 터널이 끊긴다. Customer Gateway를
  교체하고 온프레미스 쪽 remote 주소를 함께 맞추기 전까지 복구되지 않는다.
- 터널을 하나만 구성하므로 AWS가 나머지 터널을 유지보수하는 동안에도 단절될 수 있다.
  이 연결은 필수 서비스 경로가 아니며 그 전제가 깨지면 이중화를 다시 결정한다.
- traffic selector 밖의 대역은 통신할 수 없다. 다른 VLAN을 AWS와 잇는 것은 selector와
  방화벽 규칙을 함께 넓히는 별도 변경이다.
- `NET-03`의 RFC1918 선차단 때문에 VLAN에서 AWS 대역으로 가려면 그보다 앞선 허용 규칙이
  필요하다. 이 규칙은 임시이며 `NET-04`가 실제 통신표로 다시 판정한다.
- VPN state에는 tunnel pre-shared key가 평문으로 들어간다. state와 plan 파일은 저장소
  밖에서 사람이 지켜야 한다.
- 연결을 내리면 AWS 쪽 자원은 사라지지만 OPNsense 쪽 설정은 남는다. 두 쪽을 함께
  되돌리는 것은 사람의 절차이며 runbook이 소유한다.

## 재검토 조건

- VPC가 둘 이상 필요해지거나 다른 사이트가 추가되어 라우팅 허브가 실제로 쓰인다.
- 이 연결 위에 중단되면 안 되는 통신이 올라가 터널 이중화가 필요해진다.
- 온프레미스 WAN이 고정 주소가 되거나, 반대로 주소 변경이 잦아 운영이 불가능해진다.
- AWS와 통신할 VLAN이 늘어 selector를 대역 단위로 관리해야 한다.
- `KMS-01`이 Vault auto-unseal을 도입해 AWS 의존성이 복구 경로에 들어온다.
- `NET-04`가 실제 통신표로 VLAN 규칙을 최소화한다.
