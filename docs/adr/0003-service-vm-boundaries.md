# ADR-0003: 서비스 VM 경계

- 상태: `Accepted`
- 날짜: 2026-07-30
- 관련 작업: `VM-01`, `PG-01`, `MINIO-01`, `NB-01`, `WG-01`

## 배경

모든 서비스를 k3s에 넣으면 클러스터 재구축, 데이터 복구와 원격 접근 복구가 하나의 실패 순서에 묶인다. 반대로 모든 서비스를 별도 VM으로 분리하면 자원과 운영 지점이 과도하게 늘어난다. VM 분리는 같은 물리 호스트에서 HA를 만들지는 않지만 권한, 네트워크, 업데이트와 복구 단위를 나눌 수 있다.

## 결정

단일 k3s VM은 플랫폼 애플리케이션과 GitOps 워크로드를 실행한다. PostgreSQL과 MinIO는 데이터 복구를 클러스터 재구축과 분리하기 위해 전용 VM을 사용한다. Warpgate는 특권 세션 경계를, NetBird는 인터넷에 닿는 원격접속 제어면을 분리하기 위해 각각 전용 VM을 사용한다.

Linux VM은 Rocky Linux Minimal과 공통 Ansible baseline을 기본값으로 한다. 제품의 공식 지원이나 검증 결과가 요구할 때만 OS 예외를 기록한다. LXC는 기본 배치 단위로 사용하지 않는다.

## 검토한 대안

- **모든 서비스를 k3s에 배치:** GitOps는 단순해지지만 클러스터 장애가 DB·백업 착지점·원격 복구까지 함께 중단시킨다.
- **모든 제품을 개별 VM으로 배치:** 격리는 늘지만 메모리, 패치와 백업 지점이 과도하게 증가한다.
- **소형 서비스를 LXC로 배치:** 자원 효율은 좋지만 VM·cloud-init·Ansible 기준선과 다른 수명주기 및 호스트 결합이 추가된다.

## 결과

- PostgreSQL·MinIO·접근 서비스는 k3s를 재구축하는 동안 독립적으로 복구할 수 있다.
- VM별 방화벽과 자격증명 경계를 적용할 수 있다.
- 모든 VM이 같은 Proxmox에 있으므로 물리 장애는 계속 전체 중단이다.
- 제품 수가 늘기 전에 실제 CPU·RAM·disk를 다시 측정해야 한다.

## 재검토 조건

- 두 번째 물리 노드나 프로젝트 전용 NAS를 확보한다.
- 제품이 특정 OS, 배포 방식 또는 Kubernetes operator를 공식 요구한다.
- 측정 결과 VM 고정 비용이 플랫폼 서비스 수용을 방해한다.
